The Context Keeper

Learn Python's with statement by watching it manage a resource, end to end.

The Problem: In Java, you use try-with-resources to promise the JVM: "open this thing, use it, then close it for me." Python's with statement does exactly that — but the mechanism is more visible.

What you'll see: Pick a scenario below and watch a resource (a file, a database, a lock) flow through four stages: enter, use, exit, cleanup. Each stage maps to real Python code you'd write.

Python The with Statement

Manages resources in a single scope:

with open('file.txt') as f: # Use f here lines = f.readlines() # f is closed automatically

The context manager promises: when you exit this block (normally or by exception), cleanup runs.

Java try-with-resources

Same idea, different syntax:

try (FileReader f = new FileReader("file.txt")) { // Use f here String text = f.read(); } // f closes automatically

Both promise: allocate in the parens, use in the block, close at the brace.

Anatomy of a Context Manager

Under the hood, a context manager is a class with two special methods:

The Class
class FileContext: def __enter__(self): # Setup: open the resource return self.file def __exit__(self, exc_type, exc_val, exc_tb): # Cleanup: always runs self.file.close()
Using It
with FileContext() as f: # After __enter__ data = f.read() # __exit__ called here # (or after an exception)

The key insight: __exit__ always runs, even if an exception flies. That's the guarantee — cleanup is not optional.

A Closer Look: Exception Handling

When an exception happens inside the with block, Python calls __exit__ with the exception details:

def __exit__(self, exc_type, exc_val, exc_tb): # exc_type: what error? (e.g. ValueError) # exc_val: the actual error object # exc_tb: the traceback # If you return True, you suppress the exception # If you return False (or nothing), it propagates if exc_type is IOError: # Maybe log it, then suppress log("File error, recovering...") return True # Don't raise

TL;DR: The context manager sees every exception and decides: suppress it or let it through. This is why with is safer than try/finally.

Why use `with` instead of try/finally?
The with statement is cleaner and guaranteed to work. If you write try/finally by hand, you can forget the finally block, or you can mess up the cleanup code. Context managers make it explicit: cleanup happens, period.
What's the difference between `__enter__` and `__exit__`?
__enter__ is called when you enter the block (setup). It should return the thing you want to use (the file, the lock, whatever). __exit__ is called when you leave the block (cleanup), whether you left normally or threw an exception. It receives the exception info (if any) and should return True to suppress the exception, or False/None to let it through.
Can I use `with` with multiple resources?
Yes! with accepts multiple context managers in one statement:
with open('a') as f1, open('b') as f2: # Both f1 and f2 are open

Python exits them in reverse order, so if f1's close fails, f2 still gets cleaned up.

When would I write my own context manager?
Anytime you have a resource that needs guaranteed cleanup. Examples: database connections, file locks, temporary directories, timing a section of code, changing and restoring state (like a config setting). Anything where "always clean up" is the rule.
